How to work through this

Findings are ordered by severity, and that is also the order they should be fixed in. Three rules matter:

  1. Fix the architecture issue first. vuln-0008 (renderer privilege posture) is the root cause behind several other findings. Once nodeIntegration is disabled and navigation is guarded, the impact of the IPC and DOM findings drops sharply.
  2. Rotate exposed secrets. Two findings expose credentials that already shipped in distributed builds. No code change makes a leaked password safe; rotate it at the provider.
  3. Do not regress behaviour silently. The renderer reaches Electron through require('electron') at src/App.tsx:704, 738, 1178, 1183. Those call sites must keep working through a preload bridge; playback of a remote item and the telemetry toggle are the acceptance tests.

A fix is verified when: (a) the proof-of-concept in its section no longer succeeds, (b) legitimate flows still work (IPTV login, playlist load, EPG load, remote playback, statistics window), and (c) npm run lint and npm test pass.

ID: vuln-0008 Severity: CRITICAL Found: 2026-11-06 22:25:16 UTC Target: Doggy Player (Electron desktop application) CWE: CWE-669 CVSS: 9.6 Confidence: High Fix Effort: Medium

Description

The Electron main window is created with nodeIntegration: true, contextIsolation: false and webSecurity: false, and createWindow() registers no will-navigate, will-redirect, setWindowOpenHandler or will-attach-webview guard. Nothing constrains the main window to the application's own origin.

As a result, any content that reaches the network stack of the player can replace the application document with an attacker-controlled page that keeps full Node.js privileges. Two independent primitives were confirmed on a headless Electron 38.8.6 instance configured with the identical webPreferences:

  • Assigning location.href to a foreign origin navigates the top-level document; the new document executed require('fs').readFileSync('/etc/hostname') successfully.
  • window.open(...) from the application page created a second BrowserWindow whose effective preferences were nodeIntegration: true, contextIsolation: false, webSecurity: false, sandbox: false; the popup executed require('os') and reported the renderer's Node version.

Because this player loads user- and provider-supplied URLs (IPTV/VOD stream and playlist URLs entered into the "Stream URL" / "M3U Playlist URL" fields, and channel entries inside a provider's playlist), a URL that resolves to an HTML document rather than a media stream already supplies the attacker with a same-window navigation. The absence of the guard turns an ordinary "play this URL" interaction into code execution under the user's Windows account.

Impact

Confirmed on a live Electron instance: a document from a foreign origin runs inside the main window and can read arbitrary local files; window.open spawns a second fully-privileged window even after the first is compromised. Actual consequence in this product: arbitrary code execution as the logged-in Windows user — reading all documents, credentials in the user profile and in the browser profile, the Xtream credentials the app persists in localStorage (doggy_xtream_url/user/pass), writing the updater's configuration and binaries, and persistence. The attacker's only prerequisite is that the user plays a provider- or link-supplied URL that resolves to HTML instead of media.

Counterevidence

Actively sought the guards that would rule this out. (a) electron/main.js contains no will-navigate, will-redirect, setWindowOpenHandler, will-attach-webview or shell.openExternal call — grep across both trees returns nothing, so no cancellation exists. (b) The renderer itself contains no location.href, location.assign, window.open, target= or dangerouslySetInnerHTML (verified against the raw bytes of src/App.tsx), so the application does not navigate away on its own; the pivot must come from a URL the player is asked to load. That constrains the trigger but does not remove it, because the product's primary feature is loading third-party URLs. (c) Electron's sandbox is not enabled, so there is no renderer sandbox to contain the resulting process. (d) A mitigating factor considered and rejected: contextIsolation:false alone would be a defence-in-depth nit; combined with nodeIntegration:true and a missing navigation guard it is precisely the escalation. (e) The one real constraint is that the malicious URL must resolve to a document rather than a media stream; a provider that hosts their playlist UI on the same host they serve media from satisfies this trivially.

What Would Change This Severity

If the application were changed so every playable URL is validated in the main process (scheme allowlist plus content-type check) before reaching the renderer, the practical trigger would narrow considerably and the rating would drop; conversely, a demonstration that a normal provider playlist can drive the navigation without any user click would confirm the zero-interaction worst case at the same critical rating but with lower attack complexity.

Technical Analysis

Root cause — one window object with two omitted guards and three weakened preferences.

createWindow() at electron/main.js:568 builds the only application window:

    webPreferences: {
      nodeIntegration: true,
      contextIsolation: false,
      webSecurity: false
    }

electron/main.js was searched for will-navigate, will-redirect, setWindowOpenHandler and will-attach-webview; none exist. The only webContents listener registered in createWindow() is console-message (line 586). The window therefore accepts every navigation Electron would otherwise let through, and the renderer keeps Node privileges across the origin change — this is the classic Electron navigation-escape-to-RCE pattern.

Why the three preferences matter individually:

  • nodeIntegration: true puts require in the page's main world; the reproduced foreign page executed require('fs').
  • contextIsolation: false means even a future preload would share a world with page script, so no bridge-based boundary exists today.
  • webSecurity: false disables the same-origin policy for fetches inside the window; the reproduction read https://example.org/ from a page on a different origin and received HTTP 200, so a foreign document can both read attacker infrastructure and, more importantly, needs no CORS cooperation to do anything it wants.

Why window.open matters independently of location.href: with no setWindowOpenHandler, Electron's default is to create a child BrowserWindow that inherits the parent's webPreferences. The reproduction read back the child's effective preferences (nodeIntegration: true, contextIsolation: false, webSecurity: false, sandbox: false) and executed Node in the child. This means a navigation guard added only to the parent window would be bypassed by a single window.open call.

Reachability from the product's own inputs: the renderer accepts arbitrary URLs for playback. handleOpenUrl() (src/App.tsx:2188) pushes the typed URL into the playlist, and provider-supplied channel URLs arrive the same way (src/App.tsx:5172, 5206, 5249). videoSrc (src/App.tsx:586) is then used in two places: handed to hls.js / set as <video src> for media, and sent to the get-stream-url IPC handler. A URL whose host returns an HTML document rather than media lands in the <video> element, which simply fails to decode; the same URL is a valid top-level document the moment anyone navigates to it, and the page has no other origin restriction.

Mitigation reproduced: with nodeIntegration:false, contextIsolation:true, sandbox:true, webSecurity:true, a narrow preload contextBridge exposing getStreamUrl/getTelemetry/setTelemetry, plus a will-navigate guard and setWindowOpenHandler returning {action:'deny'}, the same harness showed: require is undefined in the page, the bridge works, navigation to a foreign origin was prevented (window stayed on the app URL) and both window.open and <a target="_blank"> were denied with only one window remaining.

Remediation

Restore the standard Electron security posture for the main window and constrain where it may navigate.

  1. Change webPreferences to contextIsolation: true, nodeIntegration: false, sandbox: true and remove webSecurity: false. nodeIntegration is not required by the player's design: the renderer only uses require('electron') for ipcRenderer.invoke/send/on, which a preload can expose through contextBridge with a fixed, named API surface.
  2. Add an explicit navigation policy on the window: cancel will-navigate and will-redirect for any URL that is not the packaged dist/index.html document (in development, the dev-server origin), and return { action: 'deny' } from setWindowOpenHandler. Sending legitimate external links to the operating system browser through shell.openExternal after validating the scheme is the safe alternative, and the policy must be applied to every window the application creates, including the statistics window in telemetry.js.
  3. Remove webSecurity: false. Cross-origin IPTV fetches already go through the iptv-fetch main-process handler, so the renderer does not need the same-origin policy relaxed; nothing in the playback path requires it once hls.js and the media element are served from the application origin.
  4. Verify the migration against the player's two require('electron') call sites for playback (src/App.tsx:704, 738) and the telemetry toggle (src/App.tsx:1178, 1183) before shipping, because those are the capabilities that must survive the removal of nodeIntegration.

Fix Verification

Gate 1 (security closure): re-traced source → sink through the patched code. With nodeIntegration:false the page's main world has no require (reproduced: "require blocked: require is not defined"), so even a successful navigation to a foreign origin yields no Node capability. contextIsolation:true + sandbox:true keeps the preload's ipcRenderer out of page reach. will-navigate cancels any URL whose prefix is not the app origin (reproduced: window stayed on the app URL while the foreign URL appeared in the blocked list), and setWindowOpenHandler returns {action:'deny'} so no child window is created at all (reproduced: windowCount stayed 1 for both window.open and <a target="_blank">). Gate 2 (bypass review): checked the sibling paths I could reach — location.href (blocked by will-navigate), window.open (blocked by setWindowOpenHandler), anchor target=_blank (blocked, routed through the same window-open handler), and will-redirect (needs the same handler, which the patch adds). Not closed by the patch: webviewTag (still defaults to false, and will-attach-webview is proposed only as hardening) and programmatic loadURL from the main process (none occurs after createWindow). Gate 3 (preserved behaviour): the preload bridge was exercised and returned the same shape the renderer expects from ipcRenderer.invoke('get-stream-url', ...); handleOpenUrl/playback were not exercised inside the full application because the renderer bundle is not part of the supplied tree — this is a gap. Gate 4 (repository checks): no test suite, formatter or build configuration exists in the supplied trees, so nothing could be run; the patch is JavaScript and was syntax-checked only by loading it in Electron (the modified preload and main harness executed without error). The fix_before blocks are transcribed from the CRLF source and the file is CRLF throughout, so the suggestion block is line-for-line consistent. Narrowest-complete-change judgement: the preference change plus the navigation policy are both required (each alone is bypassable), and no unrelated refactor is included.

Description

The iptv-fetch IPC handler in the Electron main process acts as a general-purpose server-side request proxy. It forwards a renderer-supplied URL, HTTP method, arbitrary headers and arbitrary body to fetch() with no scheme allowlist, no host/IP filtering and no redirect policy, then returns the full response body back to the caller. Impact

Any party that can influence a URL handed to the bridge - a hostile shared activation code (which the app stores and auto-loads on next launch), a poisoned or hijacked provider, a socially engineered EPG/playlist URL, or any script running in the renderer - gets a read/write primitive into every service the user's machine can reach: Ollama/MongoDB/Redis/admin panels on 127.0.0.1, router and NAS admin interfaces on the LAN, and cloud instance metadata at 169.254.169.254/metadata.google.internal. The response body is returned in full to the caller, and because method, headers and body are also attacker-chosen, the primitive is not read-only: the proof of concept drove an internal service with a forged Authorization header and an attacker-authored JSON body. Exfiltration is trivial using the same bridge to POST the stolen data to an attacker endpoint.

Counterevidence

The strongest case against this finding is that provider-response fields never reach the bridge URL directly: series.id, s.stream_id and s.id are substituted into path segments after a constant baseUrl, so a merely malicious IPTV provider cannot retarget the origin on the Xtream paths (1592, 1681-1721). That constrains one vector but leaves the activation-code path fully attacker-controlled, and that path is persisted to localStorage and replayed by handleXtreamLogin(true) on every launch. A second argument is that the renderer already holds nodeIntegration: true, so any renderer script can call require('child_process') and is not meaningfully helped by the bridge - which is why this report is filed against the bridge as a reusable, typed primitive and scored on the remote-input path, not on the assumption of prior code execution. The strongest genuine mitigation: Node's fetch rejects file: and gopher:, so there is no local file read and no raw-socket protocol smuggling (Redis RESP, FastCGI) through this bridge; the PoC explicitly confirms both fail. Impact is therefore read/write HTTP(S) SSRF, not file disclosure or RCE, which is why confidentiality and integrity are H/H on the demonstrated internal-service read-and-write but availability is N. Finally, get-network-info and the network-type detection are unrelated and were not treated as evidence. No input validation, address filtering, redirect re-validation or authorization check exists anywhere on the iptv-fetch path; both the unauthenticated and the provider-scripted call paths were exercised.

What Would Change This Severity

If the bridge were reachable only with caller-supplied URLs but the response were not returned to the renderer, this would drop to a blind-SSRF Medium; conversely, if the renderer can be navigated to an arbitrary origin while carrying nodeIntegration: true, the chain becomes remote code execution and the rating rises to Critical.

Remediation

  1. Enforce a URL policy in the main process before every outbound fetch: accept only http: and https:, and reject the request unless the hostname resolves exclusively to public addresses. Block 169.254.0.0/16, fe80::/10, all RFC1918 and CGNAT ranges, 100.64.0.0/10, 0.0.0.0/8, multicast and reserved space, ::1, IPv6 ULA (fc00::/7), IPv4-mapped IPv6 equivalents, and the hostnames localhost and metadata.google.internal. Do not rely on string matching for the IP check - resolve with dns.lookup({ all: true }) and test the resolved addresses, so decimal/octal/hex and 127.1 spellings are caught.
  2. Do not follow redirects implicitly. Fetch with redirect: 'manual', re-apply the full policy to every Location before following it, and cap the hop count.
  3. Restrict the request metadata the caller may set. Authorization, Cookie and custom X- headers should not be forwarded from renderer input to arbitrary hosts; if a provider needs a specific header, whitelist the exact header names per call site.
  4. As defense-in-depth against DNS rebinding between the policy check and the actual connection, resolve the hostname once and connect to that pinned address rather than letting the HTTP client re-resolve.
  5. Apply the same policy to the remote branch of get-stream-url, which currently returns a loopback transcoder URL containing any http(s) string the renderer supplies.
  6. Separately, reconsider the renderer's nodeIntegration: true, contextIsolation: false and webSecurity: false posture. While the renderer holds full Node.js privileges and has no navigation guard, any renderer code execution escalates to local code execution, and hardening this bridge alone will not prevent that. A preload with a narrow, validated IPC surface and contextIsolation: true removes both problems at once.

Remediation

  1. Stop publishing provider credentials to a third-party store in a form that anyone can read. The code must not be the only thing standing between an anonymous internet user and a stored password.
  2. Remove the implicit trust in a short numeric code: a four-digit key has 10,000 values and can be walked exhaustively. Any shareable identifier must carry real entropy (for example a 128-bit random token) so that possession of the token, rather than a guessable number, is what authorizes access.
  3. Encrypt the credential payload before it leaves the device, with a key derived from a secret the sharing user transmits out of band. The storage provider must never be able to read the plaintext, since it is not a trusted component of this system.
  4. Alternatively, if the sharing feature cannot be made safe with the current infrastructure, remove the credential-publication path entirely and let recipients enter their own login.
  5. Add expiry and a revocation control so a shared credential stops being retrievable after a bounded period or on user request.
  6. Treat the stored credentials as compromised for any user who has already created a code, and require them to rotate their provider password.

Gate 1 — applicability. Every fix_before block was copied from the file with sed/cat -A and matches character-for-character at the stated ranges (the file uses CRLF line endings and 2-space indentation in the credential code, 7-space in handleCreateCode, 23-space in the JSX); line numbers were re-checked against the live file, not the sweep's estimates.

Gate 2 — security closure. The source→sink path is handleCreateCode state → encodeForKV (base64) → UpdateValue/${KV_APP_KEY}/${generateCode}. After the patch, the write key becomes sha256("doggy-share-v1|" + code) and the value becomes AES-GCM ciphertext under a PBKDF2 key derived from the same code. The patch is functionally complete only together with the two helper functions it calls (encryptCredsForShare/decryptCredsFromShare); those helpers are not included in this suggestion and must be added — WebCrypto deriveKey+encrypt/decrypt (AES-GCM, random 12-byte IV, PBKDF2-SHA256 with a high iteration count). Technical Analysis

The favourites/folder sync uses the same public store as the activation codes but a completely different key scheme, and one that is weaker still.

getSyncKey() (src/App.tsx:1418) concatenates the provider URL and username, base64-encodes the pair and strips non-alphanumerics. The result is favs_ plus a deterministic encoding of public data. There is no salt, no per-user random value and no machine binding, so the identifier is reproducible by anyone who knows the two inputs — and a username is the least secret part of a provider account.

saveToCloud() (src/App.tsx:1424) publishes {items, folders} under that identifier through UpdateValue, and loadFromCloud() (src/App.tsx:1434) fetches the same identifier through GetValue and assigns data.items / data.folders straight into component state. The service authenticates neither direction, which was confirmed live: an arbitrary identifier returns HTTP 200 with "" when absent and the payload when present, with no header, cookie or referer involved.

The loop closes at the sync effect (src/App.tsx:1450): whenever favourites or folders change, saveToCloud republishes the current state. After a tampered read is applied via setFavorites()/setFavoriteFolders(), the victim's next change writes the injected content back to the store, so the tampered state persists across reads rather than being corrected.

This is distinct from the activation-code finding: different record family ({items, folders} rather than {url, user, pass}), different key derivation (public pair rather than a four-digit code) and a different affected population (every user who syncs, not only those who deliberately published a code).
