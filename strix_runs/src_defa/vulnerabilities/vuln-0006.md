# Hard-coded IPTV provider credential shipped in client bundle (ACTIVATION_CODES)

**ID:** vuln-0006
**Severity:** MEDIUM
**Found:** 2026-11-06 22:15:51 UTC
**Target:** Doggy Player (Electron) — src/App.tsx
**CWE:** CWE-798
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Low

## Description

A complete, ready-to-use IPTV provider credential — server URL, username and password — is hard-coded in `src/App.tsx` as the `ACTIVATION_CODES` map. Because this file is imported by the renderer entry point, the secret is compiled into every distributed build of the application and can be extracted by anyone who installs it.

## Evidence

The secret is a module-scope literal in the file the renderer imports:

```javascript title=src/App.tsx startLineNumber=1207 endLineNumber=1209
  const ACTIVATION_CODES: Record<string, { url: string; user: string; pass: string }> = {
    "6923": { url: "http://premiumtest.tr:8080", user: "hBHCQDmz", pass: "ggY6RMm" }
  };
```

It is reachable from the renderer entry point with no guard:

```typescript title=src/main.tsx startLineNumber=3 endLineNumber=3
import App from './App.tsx';
```

and it is consumed as a plain lookup on a user-supplied code:

```javascript title=src/App.tsx startLineNumber=1270 endLineNumber=1275
      const creds = ACTIVATION_CODES[activationCode.trim()];
      if (creds) {
        setXtreamUrl(creds.url); setXtreamUser(creds.user); setXtreamPass(creds.pass);
        localStorage.setItem('doggy_xtream_url', creds.url);
        localStorage.setItem('doggy_xtream_user', creds.user);
        localStorage.setItem('doggy_xtream_pass', creds.pass);
```

No encryption, obfuscation, remote-config indirection, or runtime gate surrounds the value. Search of the repository for any wrapper around it (`rg -n "ACTIVATION_CODES" src/App.tsx`) returns only the declaration and this single call site.

## Impact

The provider account `hBHCQDmz` on `http://premiumtest.tr:8080` is exposed to every person who installs Doggy Player, with no reverse engineering beyond string extraction from the shipped bundle. Anyone can use that login directly against the provider's player API — streaming the subscription's channels and VOD, and reading the account's user info — or enter `6923` in the app's own Activation Code field to adopt it. The credential cannot be rotated by users because they do not own it; it belongs to the developer, so the exposure persists for every future build until the literal is removed and the password changed.

## Counterevidence

The strongest argument against this finding is that the credential may be a throwaway test account — the host is `premiumtest.tr` and the verification path is the "Activation Code" tab, which is a convenience feature rather than the product's main login. If the account is disabled or is a sandbox with no entitlement, the practical impact is limited to a leaked identifier rather than usable access. That argument does not make the pattern safe: the value is a complete, syntactically valid Xtream credential set (server, username, password) wired into a user-facing login path, so if it is live it is immediately usable, and if it is not live it is still a credential committed to source that will be harvested and reused. I checked for any control that would prevent extraction: the constant is at module scope in `App.tsx`, not behind a runtime gate, not fetched from a config service, and not obfuscation-protected, so it is present verbatim in the built renderer bundle in every distributed copy. I also confirmed the code path at `src/App.tsx:1270` compares the user-typed code against this map directly with no secret, so anyone who extracts the map can also use that code. Nothing in the repository encrypts, wraps, or scopes this value.

## Confidence Rationale

The credential literal and its consumption path were read directly from the shipped source that `main.tsx` imports; the mechanism (module-scope const serialized into the renderer bundle) is deterministic. The only unverified element is the live provider account's current validity, which does not affect whether the secret ships in the client.

## What Would Change This Severity

Confirmation that `hBHCQDmz` on `premiumtest.tr` is a currently active, paid subscription with content entitlement would raise the impact, since it would mean a live account is exposed to every installer; evidence that the account is already disabled would lower it to a hygiene issue.

## Technical Analysis

**The secret.** `src/App.tsx:1207-1209` declares a map from activation code to a full Xtream credential set:

```javascript title=src/App.tsx startLineNumber=1207 endLineNumber=1209
  const ACTIVATION_CODES: Record<string, { url: string; user: string; pass: string }> = {
    "6923": { url: "http://premiumtest.tr:8080", user: "hBHCQDmz", pass: "ggY6RMm" }
  };
```

**Why it ships.** `src/main.tsx:3` imports `App.tsx` as the renderer root, so `App.tsx` is not a developer-only or test-only module — it is the production entry point that Vite bundles into the distributed renderer JavaScript. A module-scope `const` holding a string literal is emitted verbatim into that bundle. Any recipient of the application therefore receives the credential, and extraction requires nothing more than opening the bundle in a text editor or using `strings`.

**The path.** `handleActivationLogin` (`src/App.tsx:1264`) looks the typed code up in this map ahead of any network call:

```javascript title=src/App.tsx startLineNumber=1270 endLineNumber=1277
      const creds = ACTIVATION_CODES[activationCode.trim()];
      if (creds) {
        setXtreamUrl(creds.url); setXtreamUser(creds.user); setXtreamPass(creds.pass);
        localStorage.setItem('doggy_xtream_url', creds.url);
        localStorage.setItem('doggy_xtream_user', creds.user);
        localStorage.setItem('doggy_xtream_pass', creds.pass);
        setIptvMode('xtream');
        await handleXtreamLogin(false, creds.url, creds.user, creds.pass);
```

The values flow straight into the provider's `player_api.php?username=...&password=...` request, so the literal is not a placeholder — it is a working credential format that the application itself treats as valid authentication material.

**Root cause.** The activation code doubles as a delivery mechanism for a developer-owned credential. That design couples "the user knows a code" to "the user obtains a password", which cannot be done safely in a client-distributed artifact: any mechanism that supplies a secret to the client also supplies it to every client. The correct pattern keeps the secret server-side and lets the client present only an opaque token.

**Exposure scope.** One account. Unlike the sharing-code issue, this is not a cross-user leak — it is a developer credential exposed to all users. Severity is driven by whether the account carries a live subscription, which was not determined here; the source-level exposure itself is certain.

## Proof of Concept

1. Obtain a distributed build of Doggy Player (or read `src/App.tsx`, which is compiled verbatim into the renderer bundle).
2. Locate the `ACTIVATION_CODES` declaration and extract the `url`, `user` and `pass` values.
3. Use those values directly against the provider's Xtream API endpoint (`<url>/player_api.php?username=<user>&password=<pass>`) to authenticate as the account owner.
4. Alternatively, type the code `6923` into the app's Activation Code field, which stores the same credential set into `localStorage` under `doggy_xtream_pass` and logs in automatically.

```python
#!/usr/bin/env python3
"""Extracts the hard-coded Xtream credential from the renderer source and
confirms it is a syntactically complete credential set that the app feeds
straight into its login routine. No request is made to the provider."""
import re
from pathlib import Path

src = Path("src/App.tsx").read_text(encoding="utf-8", errors="replace")

m = re.search(
    r'ACTIVATION_CODES[^=]*=\s*\{(.*?)\};',
    src,
    re.S,
)
block = m.group(1)
entry = re.search(
    r'"([^"]+)"\s*:\s*\{\s*url:\s*"([^"]+)"\s*,\s*user:\s*"([^"]+)"\s*,\s*pass:\s*"([^"]+)"\s*\}',
    block,
)
code, url, user, password = entry.groups()
print(f"activation code : {code}")
print(f"provider url    : {url}")
print(f"username        : {user}")
print(f"password        : {password}")
print()
print("app login URL would be:")
print(f"  {url.rstrip('/')}/player_api.php?username={user}&password={password}")
print()
print("[CONFIRMED] complete credential set embedded in client-delivered source")
```

## Remediation

1. Remove the hard-coded `ACTIVATION_CODES` entry from the renderer source and treat the embedded account as compromised — rotate its password immediately, because it has already shipped in every build.
2. Do not embed any credential that must remain secret in client-delivered code; anything in the bundle is public by definition. If a built-in activation path is genuinely required, have the client present an opaque code to a service you control and let that service perform the provider login, so the secret never reaches the device.
3. Add automated secret scanning (a pre-commit hook plus a CI gate over the renderer sources) to prevent credential literals from being reintroduced.
4. Audit the rest of the shipped bundles for other embedded secrets, and review whether build tooling is excluding developer-only constants from production output.

## Fix Verification

**Gate 1 — applicability.** The block at `src/App.tsx:1204-1209` was copied with `sed`/`cat -A` and matches the file exactly, including the 2-space indentation and CRLF line endings; line numbers were verified against the live file rather than the static sweep's estimate. The change is confined to a single declaration.

**Gate 2 — security closure.** The sink is the shipped bundle: `main.tsx` imports `App.tsx`, so anything at module scope in `App.tsx` is serialized into the renderer output. After the patch the map is empty, so there is no literal credential left anywhere in the source tree for a bundler to emit, and the only remaining path to credentials is the sharing flow (addressed separately). Traced the call site at `src/App.tsx:1270` and confirmed that an empty map yields `creds === undefined`, which falls through to the existing `if (creds)` guard and then to the network lookup — no new failure mode, and the credential simply stops existing client-side.

**Gate 3 — bypass review.** Searched the whole repository for the password, the username and the host to confirm there is no second copy (including a second map entry, a fallback constant, or a duplicate in `electron/`). Confirmed the `Record<...>` type annotation is preserved so any other reference still typechecks. Considered the alternate input class: a user typing `6923` after the patch reaches the network branch and receives the same "invalid code" alert as any unknown code, so behaviour degrades gracefully.

**Gate 4 — preserved behaviour.** The activation-code feature's shape is untouched — the map, its type, the lookup and the fallthrough branch all remain. Only the single hard-coded account is removed. If the maintainer intends to keep a built-in code, this patch would remove it and that is a deliberate product decision, which is why the PR body calls it out explicitly.

**Gate 5 — repository checks: GAP.** This checkout provides only `src/` and `electron/`; there is no `package.json`, no dependency installation and no build or typecheck configuration, so `tsc` and the Vite build could not be executed. The edit is a one-line value change inside an existing annotated declaration and is syntactically inert, but it has not been compiler-verified.

## Assumptions

Assumes distributed builds are produced from this source as-is (a Vite renderer bundle, per the `vite-env.d.ts` and `main.tsx` entry point), which places the literal in the shipped JavaScript. Exploitation requires only possession of the installer, which is the intended distribution channel.
