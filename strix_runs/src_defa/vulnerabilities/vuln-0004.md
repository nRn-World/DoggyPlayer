# Hostile IPTV playlist controls image request origin via unvalidated tvg-logo in the M3U parser

**ID:** vuln-0004
**Severity:** MEDIUM
**Found:** 2026-11-06 22:11:59 UTC
**Target:** Doggy Player src/App.tsx M3U playlist ingestion
**Endpoint:** src/App.tsx
**Method:** N/A
**CWE:** CWE-79
**CVSS:** 4.2
**Confidence:** High
**Fix Effort:** Low

## Description

The M3U loader copies tvg-logo, group-title and the channel name from attacker-controlled playlist text into React state with no validation. tvg-logo is bound to a live img src, so the IPTV provider chooses the URL scheme and host of image requests made by the privileged renderer.

Parsed output: the icon field holds the data or file URI verbatim, and the category and name fields keep the inline markup.

Rendered observation in headless Chromium: img.src resolves to the base64 data image svg URI supplied by the playlist, the channel name renders as literal text, and no handler fires (the xss detection object stays empty).

The same playlist through the proposed parse-time validation yields name Channel, icon empty, category News and an unchanged http stream URL.

## Impact

A hostile playlist forces the renderer to GET URLs of the provider's choosing (data, file, or any reachable http host) with the playlist as the only precondition. The renderer runs with nodeIntegration true and webSecurity false, so an origin it is made to load is readable by the application.

## Counterevidence

Actively tried to escalate and could not, in four directions.

Script execution via the data SVG: probed in headless Chromium with an SVG containing a script element. The image loads (naturalWidth 120) but the script does not run, so no XSS is claimed.

Markup in channel name, category and EPG fields: fed img with onerror and svg with onload through the real parser and the identical render expressions. All landed as textContent, no handler fired, and a repo-wide grep found no dangerouslySetInnerHTML, innerHTML or insertAdjacentHTML anywhere in src/ (the only hit is a date chart in a statistics document that never renders playlist data).

Local-file stream URLs: rejected by the line.startsWith http gate at App.tsx:1628. Verified directly: a file URL line placed inside a channel block produces zero items. The local-path branch also requires a real File object from the OS picker.

Loopback read through the player own media server: refused without the token. A request to 127.0.0.1 stream endpoint with a wrong token returned 403 Forbidden; the token guard is at electron/main.js:717 and the token is not obtainable from playlist content.

What survives: the provider fully controls the origin of image requests issued by a renderer that has webSecurity false and Node integration, plus markup carried unvalidated into labels. Nothing on the parse path constrains either, and no control was found that runs before the icon reaches the attribute.

## Confidence Rationale

Parser behaviour, rendered DOM and the negative controls were reproduced directly in this environment.

## What Would Change This Severity

Proof that a data or file image source yields a readable body would raise this to High; removing webSecurity false or nodeIntegration would lower it to Low.

## Technical Analysis

handleM3ULogin fetches the playlist through the iptv-fetch bridge and splits it on newlines. For every EXTINF line it extracts three fields with no validation at src/App.tsx:1622-1627: name from the text after the last comma, icon from the tvg-logo attribute, and group from the group-title attribute. All three are stored directly in state and are never revisited by any later check.

The icon reaches a live attribute in five places: src={item.icon} at src/App.tsx:3915 (the primary IPTV grid the user lands on), 4314, 5174, 5208 and 5251. Because no scheme constraint is applied, the value can be a data URI, a file URL, or any http host the provider names. The browser resolves it and issues the request from the renderer origin.

The group and name reach JSX text children at src/App.tsx:4289 (category label) and 3918, 4316 and 5251 (channel labels). They are rendered as text nodes, so the markup is displayed rather than parsed, but the raw string is retained in state and used as a React key and as a lookup identifier.

The loop contains exactly one filter and it applies only to the stream line: line.startsWith http at line 1628. That is why local media paths are not reachable through the playlist, and it is also why the metadata fields were never considered.

The consequence is amplified by the window configuration at electron/main.js:573-579: nodeIntegration true, contextIsolation false and webSecurity false. An origin that the player is induced to request is therefore readable by application code, which is not true of an ordinary sandboxed renderer.

## Remediation

Validate every playlist field at parse time, before it enters state, in handleM3ULogin.

1. Resolve stream and logo values with the URL API against the playlist base and keep only http and https. Reject anything else by returning an empty string rather than storing the raw value.
2. Require the playlist base itself to be http or https so a dangerous scheme cannot be inherited through relative resolution.
3. Reduce channel and category labels to plain text: strip tag spans, collapse control characters and whitespace, trim, and cap the length.
4. Drop a channel whose URL does not pass the scheme check, and stop treating any line beginning with a hash as a candidate stream URL.

The accompanying change set implements exactly this. Separately, consider removing webSecurity false and nodeIntegration from the main window so that any future rendering gap does not also grant filesystem and cross-origin read authority.

## Fix Verification

Security closure (executed + traced). The sink is src={item.icon} at App.tsx:3915, 4314, 5174, 5208 and 5251. In the patched loop icon can only hold the result of cleanUrl, which returns an empty string unless new URL(raw, streamBase).protocol is http or https, so a data, file, javascript or protocol-relative value can no longer reach the attribute. name and group pass through cleanText, which removes tag spans before they enter state. streamBase is rejected unless the user playlist URL is itself http(s), so the base cannot supply a dangerous scheme. Verified by running the patched logic over the hostile playlist: icon came back empty and category came back as News.

Bypass review (executed). Cases exercised through the patched block: file URL, javascript scheme, data image svg base64, data text html base64, protocol-relative host path, uppercase HTTP scheme, playlist-relative logo path, and hash comment lines. The dangerous values are dropped or emptied, relative http logos still resolve against the playlist base, and comment lines are ignored by the leading-hash guard. Sibling call sites checked: handleOpenUrl at App.tsx:2189 is a user-typed box rather than playlist data; handleXtreamLogin builds URLs only from the user own base URL, so neither needed a change.

Preserved behaviour (executed). Compiled the patched block with tsc target ES2020 lib ES2020,DOM in strict mode and ran it over a mixed playlist: two ordinary http streams survive with their names and the News and Movies categories, and a relative logo path becomes absolute. Empty icons degrade to the existing onError fallback in the UI.

Gap. The checkout has no test suite or lint configuration, so tsc strict noEmit on the new code is the narrowest available check and it passes. A full vite build was not run because it needs the project own toolchain and dependency install; that is the only gate I could not execute.
