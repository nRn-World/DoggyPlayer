# Favourites and folder sync stores per-user data in a public unauthenticated store under an identifier derived only from provider URL and username, allowing cross-user read and overwrite

**ID:** vuln-0010
**Severity:** MEDIUM
**Found:** 2026-11-06 22:42:49 UTC
**Target:** Doggy Player (Electron desktop application)
**CWE:** CWE-639
**CVSS:** 4.2
**Confidence:** Medium
**Fix Effort:** Medium

## Description

The favourites and folder sync writes each user's playlist metadata into the same public, unauthenticated key-value store used for activation codes, under an identifier derived only from the provider URL and the account username. Neither value is a secret: the provider host is visible to other users of the service, and the username is a normal account identifier. Anyone who knows or guesses the pair can compute the identical identifier and read that user's favourites, then overwrite them.

The read path is also the app's normal sync path, so injected data is consumed and re-published on the next local change. This is a separate flaw from the activation-code sharing: it involves a different record family, a different key-derivation scheme, and affects every syncing user rather than only those who chose to create a code.

## Impact

Anyone who learns a user's provider host and username — both of which circulate in the activation-code records and in provider account identifiers — can read and rewrite that user's favourites and folder structure. Because the sync reads the remote copy on every sync cycle, injected content is applied to the victim's UI and then persisted locally on the next change. The data itself is playlist metadata (favourite identifiers, folder names), not credentials, so the confidentiality impact is limited; the integrity impact is that a third party can silently alter what the user sees and keeps, with no authentication at any point.

## Counterevidence

Actively looked for controls that would rule this out. (a) Is the key secret? No: `getSyncKey()` (`src/App.tsx:1418-1422`) is a pure function of `xtreamUrl` and `xtreamUser` with no user secret, and the harness shows a stranger reproducing the owner's key from those two values alone; the only variation is which username is used, so it is guessing-resistant only by the provider's own username format. (b) Is there any read authorization on the store? No — confirmed against the live service, an arbitrary-key `GetValue` returns 200 with the payload and needs no header. (c) Does the sync overwrite the server copy before reading it, so an attacker's injected data is actually consumed? Yes: `loadFromCloud` (`src/App.tsx:1434`) only reads, but the sync effect (`src/App.tsx:1450`) calls `saveToCloud` on favourites/folder changes, so a legitimate `setFavorites()` from a tampered read is written back under the same key on the next change, completing the loop. (d) Is the impact limited to playlist metadata? Yes — the payload is `{items, folders}`, i.e. favourite identifiers and folder names, with no credential and no path outside the favourites UI, which is why this is rated low rather than high. (e) What genuinely reduces confidence is population: the identifier is derived from a pair the attacker must know, and I did not locate a live record to confirm how many exist, so the exposure is real in mechanism but unquantified in practice.

## Confidence Rationale

The key derivation, the unauthenticated read/write endpoints and the write-before-read ordering in `loadFromCloud` were all confirmed in the shipped source and reproduced in a Node harness; the service's lack of reader authorization was confirmed live against the same namespace on a different record family. The gap is that no live favourites record was located or modified: the derivation requires both the provider host and the account username, and the population of this record family was not established. A populated record's existence is therefore inferred from the automatic sync behaviour rather than observed.

## What Would Change This Severity

Confirmation that a populated favourites record exists for a live user (demonstrating the derivation lands on real data) would raise confidence and impact; evidence that the sync feature is disabled in shipped builds would drop this to informational.

## Technical Analysis

The favourites/folder sync uses the same public store as the activation codes but a completely different key scheme, and one that is weaker still.

`getSyncKey()` (`src/App.tsx:1418`) concatenates the provider URL and username, base64-encodes the pair and strips non-alphanumerics. The result is `favs_` plus a deterministic encoding of public data. There is no salt, no per-user random value and no machine binding, so the identifier is reproducible by anyone who knows the two inputs — and a username is the least secret part of a provider account.

`saveToCloud()` (`src/App.tsx:1424`) publishes `{items, folders}` under that identifier through `UpdateValue`, and `loadFromCloud()` (`src/App.tsx:1434`) fetches the same identifier through `GetValue` and assigns `data.items` / `data.folders` straight into component state. The service authenticates neither direction, which was confirmed live: an arbitrary identifier returns HTTP 200 with `""` when absent and the payload when present, with no header, cookie or referer involved.

The loop closes at the sync effect (`src/App.tsx:1450`): whenever favourites or folders change, `saveToCloud` republishes the current state. After a tampered read is applied via `setFavorites()`/`setFavoriteFolders()`, the victim's next change writes the injected content back to the store, so the tampered state persists across reads rather than being corrected.

This is distinct from the activation-code finding: different record family (`{items, folders}` rather than `{url, user, pass}`), different key derivation (public pair rather than a four-digit code) and a different affected population (every user who syncs, not only those who deliberately published a code).

## Proof of Concept

1. Read `getSyncKey()` and confirm it is built only from `xtreamUrl` and `xtreamUser`, with no secret component.
2. Reproduce the derivation for a target provider host and username; the resulting `favs_<base64>` string matches the owner's identifier exactly.
3. Request `https://keyvalue.immanuel.co/api/KeyVal/GetValue/<namespace>/<derived key>` with no authentication to retrieve the stored `{items, folders}` payload.
4. Write a modified payload to `https://keyvalue.immanuel.co/api/KeyVal/UpdateValue/<namespace>/<derived key>/<base64>`, which the service accepts without credentials.
5. Confirm from the source that `loadFromCloud()` applies the fetched `items` and `folders` directly to component state, so the injected payload is consumed on the victim's next sync and re-published on the next favourites change.

```js

// Attacker only needs the public provider host and account username.

// Unauthenticated read (same endpoint the app's loadFromCloud uses).

fetch(url).then(r => r.text()).then(body => {
  console.log('stored payload:', body);
  // A modified payload can be written back the same way the app's saveToCloud does:
  //   PUT-style UpdateValue/bjlqbgku/<ownerKey>/<base64 of {items, folders}>
});
```

## Remediation

Stop deriving the cloud identifier from provider details. Mint a per-install random token (at least 128 bits) on first run, keep it in local storage, and key the sync records by that token so the identifier cannot be computed by a third party who knows the provider host and username. Refuse to apply a fetched record when the local install has never minted a token, which prevents an attacker's first-run write from being consumed. Treat the current favourites records as exposed — they contain playlist identifiers and folder names — and plan their migration to the new key scheme. The durable fix, as with the activation-code sharing, is a backend you operate that authenticates the reader and refuses writes to records the caller does not own; removing derivability alone does not stop unauthenticated writes to a leaked identifier.

## Fix Verification

Gate 1 (security closure): after the patch the record identifier is `favs_<random per-install token>` where the token is minted once and persisted locally, so it cannot be derived from the provider URL or username; a stranger who knows both cannot compute the key that `UpdateValue`/`GetValue` are invoked with (the trace ends at the same `ipcRenderer.invoke` sink with a value the attacker cannot produce). `loadFromCloud` additionally refuses to apply a payload when the locally stored token is absent, so a first-run attacker write is not consumed. Gate 2 (bypass review): checked the other writer that touches favourites (`saveToCloud` callers) — both read the key from the same `getSyncKey()`, so the single change covers write and read; checked the m3u branch (`mainIdentity = m3uUrl`) and gave it the same token treatment; confirmed the envelope `{items, folders}` shape is unchanged so the `decodeFromKV` consumer still works. Gate 3 (preserved behaviour): the sync effect at `src/App.tsx:1450` still triggers on favourites/folder changes and the payload is still applied to `setFavorites`/`setFavoriteFolders`; the only behavioural difference is that an existing install needs one successful save before a fresh key is used, which the code handles by minting the token on first call. Gate 4 (repository checks): the supplied trees contain no `package.json`, bundler configuration or test runner, so no build, typecheck or test could be executed — this is an explicit gap. The change is a self-contained helper plus three call sites and was syntax-checked only by reasoning about the existing types.

## Assumptions

Assumes at least one user has used the favourites/folder sync, which the app performs on its own when a provider is configured (not an opt-in action). Assumes the public key-value service remains reachable and open, which it was at the time of testing.
