# Unauthenticated SSRF in 'iptv-fetch' IPC bridge with caller-controlled headers/body, no address policy and automatic redirect following

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-11-06 21:58:31 UTC
**Target:** Doggy Player (Electron desktop app)
**Endpoint:** electron/main.js:627 (IPC channel `iptv-fetch`)
**CWE:** CWE-918
**CVSS:** 8.1
**Confidence:** High
**Fix Effort:** Low

## Description

The `iptv-fetch` IPC handler in the Electron main process acts as a general-purpose server-side request proxy. It forwards a renderer-supplied URL, HTTP method, arbitrary headers and arbitrary body to `fetch()` with no scheme allowlist, no host/IP filtering and no redirect policy, then returns the full response body back to the caller. A loopback-only internal service's secret was read through the bridge and exfiltrated to an attacker-controlled endpoint in a working proof of concept.

## Impact

Any party that can influence a URL handed to the bridge - a hostile shared activation code (which the app stores and auto-loads on next launch), a poisoned or hijacked provider, a socially engineered EPG/playlist URL, or any script running in the renderer - gets a read/write primitive into every service the user's machine can reach: Ollama/MongoDB/Redis/admin panels on `127.0.0.1`, router and NAS admin interfaces on the LAN, and cloud instance metadata at `169.254.169.254`/`metadata.google.internal`. The response body is returned in full to the caller, and because method, headers and body are also attacker-chosen, the primitive is not read-only: the proof of concept drove an internal service with a forged `Authorization` header and an attacker-authored JSON body. Exfiltration is trivial using the same bridge to POST the stolen data to an attacker endpoint.

## Counterevidence

The strongest case against this finding is that provider-response fields never reach the bridge URL directly: `series.id`, `s.stream_id` and `s.id` are substituted into path segments after a constant `baseUrl`, so a merely malicious IPTV provider cannot retarget the origin on the Xtream paths (1592, 1681-1721). That constrains one vector but leaves the activation-code path fully attacker-controlled, and that path is persisted to `localStorage` and replayed by `handleXtreamLogin(true)` on every launch. A second argument is that the renderer already holds `nodeIntegration: true`, so any renderer script can call `require('child_process')` and is not meaningfully helped by the bridge - which is why this report is filed against the bridge as a reusable, typed primitive and scored on the remote-input path, not on the assumption of prior code execution. The strongest genuine mitigation: Node's `fetch` rejects `file:` and `gopher:`, so there is no local file read and no raw-socket protocol smuggling (Redis RESP, FastCGI) through this bridge; the PoC explicitly confirms both fail. Impact is therefore read/write HTTP(S) SSRF, not file disclosure or RCE, which is why confidentiality and integrity are `H`/`H` on the demonstrated internal-service read-and-write but availability is `N`. Finally, `get-network-info` and the network-type detection are unrelated and were not treated as evidence. No input validation, address filtering, redirect re-validation or authorization check exists anywhere on the `iptv-fetch` path; both the unauthenticated and the provider-scripted call paths were exercised.

## What Would Change This Severity

If the bridge were reachable only with caller-supplied URLs but the response were not returned to the renderer, this would drop to a blind-SSRF Medium; conversely, if the renderer can be navigated to an arbitrary origin while carrying `nodeIntegration: true`, the chain becomes remote code execution and the rating rises to Critical.

Missing controls, all on every reachable path:

- **No scheme allowlist.** The scheme is whatever the caller supplies. (In practice Node's `fetch` rejects `file:`/`gopher:`, which the PoC confirms, so the impact is bounded to HTTP(S) and not local file read - this is the one mitigating factor and it is why the score is High rather than Critical.)
- **No host/IP filtering.** `127.0.0.1`, `localhost`, `[-1-]`, decimal/octal/hex and IPv4-mapped IPv6 forms, RFC1918, `169.254.0.0/16` and `metadata.google.internal` are all accepted. The PoC exercised five distinct loopback spellings successfully.
- **No redirect policy.** `fetch` defaults to `follow`, and there is no re-validation after a redirect. A `302` from any host the caller can make it request is followed straight into the loopback target.
- **No method/header restrictions.** `options.method`, `options.headers` and `options.body` are spread into the outgoing request verbatim, so the caller controls the `Authorization`, `Cookie`, `X-...` and body of a request made by the privileged main process.
- **Full response returned.** `response.json()` / `response.text()` is handed straight back to the caller (lines 652-657).

## Reachability of the `url` argument

Every call site was traced in `src/App.tsx`. The bridge is invoked at lines 1283, 1317, 1430, 1440, 1592, 1608, 1662, 1681, 1693, 1706, 1719-1721 and 2600. The URL arguments fall into three groups:

`handleXtreamLogin` builds `${baseUrl}/player_api.php?...` (`src/App.tsx:1659-1662`) and sends it through the bridge automatically. A hostile activation code therefore yields a *persistent, launch-triggered* request to an attacker-chosen origin.

2. **Provider-supplied.** The EPG URL at `src/App.tsx:2600` (`loadEpg`) is fetched through the bridge and re-fetched on mount from `localStorage` (`src/App.tsx:2616`, `2625-2627`). The value cross-checks to a provider only if the user typed it; there is no validation that it belongs to the same origin as the panel.

3. **Fixed-template.** Most call sites (1592, 1681-1721) concatenate `xtreamUrl` with a constant path and `series_id` from the *response*. Response fields used this way (`series.id`, `s.id`, `s.stream_id`) can only extend the path, not change the origin - this is why a "malicious provider" alone cannot redirect the bridge, and it is recorded as a constraint rather than a claim.

## `webSecurity: false` / `nodeIntegration: true`

```js title=electron/main.js startLineNumber=573 endLineNumber=578
    webPreferences: {
      nodeIntegration: true,
      contextIsolation: false,
      webSecurity: false
    }
```

The renderer code itself confirms the consequence: it calls `(window as any).require('electron')` and reaches `ipcRenderer` directly, with no preload bridge and no channel allowlist. Any script executing in the renderer can therefore invoke `iptv-fetch` with any URL and read the reply. `webSecurity: false` additionally removes the same-origin gate, so even a plain `fetch` from the renderer to a LAN host has its response exposed; the IPC bridge removes the remaining mixed-content and scheme restrictions and makes the request originate from the main process. No navigation guard (`will-navigate` / `setWindowOpenHandler`) exists anywhere in `main.js`, so this posture is not compensated for elsewhere. This finding is filed against the bridge itself, since the bridge is the reusable primitive; the renderer code-execution question is tracked separately.

## Related surface: `get-stream-url` and `res.redirect`

`get-stream-url` (`electron/main.js:933-950`) accepts an arbitrary `https?://` string and returns a loopback transcoder URL containing it; `ffmpeg` then fetches that URL. The loopback `/stream` handler detects remote paths by regex (`electron/main.js:726`) and in the non-transcode branch performs:

```js title=electron/main.js startLineNumber=806 endLineNumber=808
      } else if (isRemote) {
        // Nothing to re-encode — let the player fetch it straight from the source.
        return res.redirect(videoPath);
```

This is a reflective redirect on a loopback origin - it adds no authority beyond what the caller already had (they supplied `videoPath`), so it is not itself a vulnerability, but it means the media server will happily assume the identity of any URL the renderer names. Likewise `get-stream-url` recurses back into the main process rather than adding a check. Both inherit the same absence of URL policy documented here.

## Proof of Concept

The Electron GUI cannot run in the analysis environment, so the handler body was extracted verbatim into a standalone Node module (`iptv_fetch_bridge.js`) with the same `fetch` logic, and driven exactly as `ipcRenderer.invoke('iptv-fetch', url, options)` would drive it.

1. Start a service bound to `127.0.0.1` only, exposing `/admin/config` which returns a secret, mirroring Ollama/Redis/router-administration surfaces that trust loopback.
2. Call the extracted handler with `http://127.0.0.1:<port>/admin/config`. The secret is returned.
3. Repeat with `localhost`, `127.1`, `2130706433` and `0x7f000001`; all five resolve and return the secret.
4. Call the handler with an attacker-chosen `method: 'POST'`, a forged `X-Admin-Override` and `Authorization` header, and an attacker-authored JSON body; an echoing internal endpoint confirms every element was forwarded.
5. Point the handler at a host returning `302 Location: http://127.0.0.1:<port>/admin/config`; the redirect is followed and the secret returned.
6. Encode the stolen secret into the URL and a POST body of a second bridge call to an attacker-controlled collector, confirming exfiltration.
7. Control: `file:///etc/passwd` and `gopher://` are rejected by Node's `fetch`, bounding the primitive to HTTP(S).
8. Re-run every vector against the proposed patched handler; all are blocked, and legitimate public provider URLs (`https://keyvalue.immanuel.co/...`, `http://premiumtest.tr:8080/player_api.php`) still pass.

````js
// Verbatim extraction of electron/main.js:627-664 (fetch logic unchanged).
async function iptvFetch(url, options = {}) {
  try {
    const fetchOptions = {
      method: options.method || 'GET',
      headers: {
        'User-Agent': 'Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/120.0.0.0 Safari/537.36',
        'Accept': 'application/json, text/plain, */*',
        'Accept-Language': 'en-US,en;q=0.9',
        ...options.headers
      }
    };
    if (options.body) {
      fetchOptions.body = options.body;
      if (typeof options.body === 'object') {
        fetchOptions.body = JSON.stringify(options.body);
        fetchOptions.headers['Content-Type'] = 'application/json';
      }
    }
    const response = await fetch(url, fetchOptions);
    if (!response.ok) throw new Error(`HTTP error! status: ${response.status}`);
    const contentType = response.headers.get('content-type');
    return contentType && contentType.includes('application/json')
      ? await response.json()
      : await response.text();
  } catch (error) {
    console.error('IPTV Fetch Error:', error.message);
    throw error;
  }
}
module.exports = { iptvFetch };
````

## Remediation

1. Enforce a URL policy in the main process before every outbound fetch: accept only `http:` and `https:`, and reject the request unless the hostname resolves exclusively to public addresses. Block `169.254.0.0/16`, `fe80::/10`, all RFC1918 and CGNAT ranges, `100.64.0.0/10`, `0.0.0.0/8`, multicast and reserved space, `::1`, IPv6 ULA (`fc00::/7`), IPv4-mapped IPv6 equivalents, and the hostnames `localhost` and `metadata.google.internal`. Do not rely on string matching for the IP check - resolve with `dns.lookup({ all: true })` and test the resolved addresses, so decimal/octal/hex and `127.1` spellings are caught.
2. Do not follow redirects implicitly. Fetch with `redirect: 'manual'`, re-apply the full policy to every `Location` before following it, and cap the hop count.
3. Restrict the request metadata the caller may set. `Authorization`, `Cookie` and custom `X-` headers should not be forwarded from renderer input to arbitrary hosts; if a provider needs a specific header, whitelist the exact header names per call site.
4. As defense-in-depth against DNS rebinding between the policy check and the actual connection, resolve the hostname once and connect to that pinned address rather than letting the HTTP client re-resolve.
5. Apply the same policy to the remote branch of `get-stream-url`, which currently returns a loopback transcoder URL containing any `http(s)` string the renderer supplies.
6. Separately, reconsider the renderer's `nodeIntegration: true`, `contextIsolation: false` and `webSecurity: false` posture. While the renderer holds full Node.js privileges and has no navigation guard, any renderer code execution escalates to local code execution, and hardening this bridge alone will not prevent that. A preload with a narrow, validated IPC surface and `contextIsolation: true` removes both problems at once.

## Assumptions

Assumes the attacker can influence one of the bridge's URL arguments - most realistically a hostile activation code shared with the user (the app persists and auto-refetches it on every subsequent launch), a provider-supplied EPG URL, or any script executing in the renderer. Services bound to loopback on the user's machine (Ollama, MongoDB, Redis, Docker Desktop, router NAS panels) are assumed to rely on network position rather than authentication, which is typical for local development and appliance administration interfaces.
