# Local file read via loopback /stream?path= — no containment after the stream-token check

**ID:** vuln-0003
**Severity:** MEDIUM
**Found:** 2026-11-06 22:11:51 UTC
**Target:** /workspace/electron/main.js
**Endpoint:** /stream?path=
**Method:** GET
**CWE:** CWE-22
**CVSS:** 4.7
**Confidence:** High
**Fix Effort:** Low

## Description

The loopback media server's `/stream` route passes the request's `path` query parameter straight to `fs.createReadStream` with no containment check, from any absolute filesystem location. The only guard is a 32-hex-character random token that is deliberately printed to the application's console log alongside the same URL. Any other process on the machine that can read that console output (or the renderer console) can therefore read arbitrary local files — credential stores, config files, SSH keys — through the player's own HTTP endpoint.

## Impact

An attacker holding only local, unprivileged read access to the application's console output obtains arbitrary file read as the user running the player. Demonstrated over HTTP against a verbatim extraction of the route: `/etc/passwd` returned in full, `main.js` source returned, and traversal-escaped paths returned, while a request without the token still returned `403`. Because the route also honours HTTP `Range`, an attacker can retrieve any byte window of any file, so prefix-based redaction or tailing only the start of a file provides no protection. On the target platform the same primitive exposes the user's browser credential stores, SSH keys, and application configuration/API keys.

## Counterevidence

Actively tried to defeat the finding in four ways. (1) Remote-origin reach: a public-origin page carrying the exact valid token sent to the loopback server produced `fetch-error: Failed to fetch` and the media server logged no request, while the identical URL from curl returned `200` — Chromium's Private Network Access blocks it. (2) A `file://` page was blocked identically (`ERR:Failed to fetch`, image `NOIMG`, and no request in the server log). (3) Referer leakage: ffmpeg sends no Referer at all (`referer=-` observed at the remote receiver), and a token-bearing loopback URL navigated to a cross-origin page yields Chrome's default `strict-origin-when-cross-origin` value, which strips the query — the receiver saw `referer=http://127.0.0.1:8933/` with no token. (4) The open-redirect branch cannot be reached by app-generated URLs because `transcodeUrl()` hard-codes `&transcode=true`. What remains is that the token guard is the sole control and the token is logged by design at `main.js:750`, `main.js:812`, `main.js:894` and `src/App.tsx:714`/`744`, which is why this is rated as a local-privilege issue rather than a network one.

## Confidence Rationale

The read primitive and the absence of containment were reproduced end-to-end against a verbatim extraction of the route, including the negative control (403 without the token) and the positive control (200 with a file inside the media root after the fix). The only inference is the attacker's ability to read the console output, which the code guarantees is written at `main.js:750`, `main.js:812` and `main.js:894`.

## What Would Change This Severity

Demonstrating that a remote or browser origin can reach the loopback server with the token — for example a browser build without Private Network Access enforcement, or a token-bearing Referer-carrying hop — would raise this to High; conversely, if the packaged build shipped with console logging disabled and the URL were no longer printed, the attacker would need local log access and the rating would fall to Low.

## Technical Analysis

`startStreamServer()` (`electron/main.js:710-898`) registers exactly one route. `main.js:717` checks the token and `main.js:718` takes `req.query.path` verbatim. The subsequent flow has no normalisation, no allowlist and no root confinement anywhere:

- `main.js:726` gates only on `fs.existsSync(videoPath)` (for non-remote values), i.e. "does this path exist", not "is this path inside a media root".
- `main.js:732` stats the same raw value; `main.js:747` probes it; `main.js:767` hands it to fluent-ffmpeg as the input.
- `main.js:848` (ranged) and `main.js:879` (full file) create the read stream directly from it with `fs.createReadStream(videoPath, …)`.

The sibling helper `resolveLocalMediaPath()` (`main.js:179-189`) is the only function in the file that touches path shape at all, and it is never called from this route — and even it only strips a `file:///` prefix and decodes percent-escapes, with no containment.

The only control is the token:

```js
const streamToken = crypto.randomBytes(16).toString('hex');   // main.js:92
```

The token is not a secret in operational practice. The route logs the request path (`main.js:750`) and fluent-ffmpeg logs the full command line (`main.js:812`); the renderer logs every minted URL through the console relay at `main.js:687` and again at `App.tsx:714` / `App.tsx:744`; and the server prints the token-bearing URL at startup (`main.js:894`). Any process able to read those streams — a second, lower-privileged local user reading a captured log, or anything consuming Chromium's `--enable-logging` output — therefore holds the token.

Reach from remote origins was tested and is genuinely blocked, which bounds the finding to a local attacker: a public-origin page carrying the exact valid token received Private Network Access-blocked `Failed to fetch` responses (curl with the same URL returned `200`), a `file://` page was blocked the same way, and no token-bearing Referer reaches a remote origin (see counterevidence).

## Proof of Concept

1. Extract the `/stream` route from `electron/main.js:716-888` verbatim into a standalone Express application (`/workspace/.poc-media/server.js`), substituting only the Electron `app` object and the `ffmpeg-static` binary path.
2. Start it; it prints the random port and the token, exactly as `main.js:894` prints the URL in the real application.
3. Request `/stream?path=/etc/passwd` with no token: the response is `403 Forbidden`.
4. Request `/stream?path=/etc/passwd&token=<token>`: the response is `200` and the full contents of the file are returned.
5. Repeat with `/workspace/electron/main.js` and with a traversal path (`/workspace/.poc-media/files/../../../../etc/hostname`): both return `200` and the file contents.
6. Send `Range: bytes=700-800` with a valid token: the response is `206` with that byte window of `/etc/passwd`, demonstrating arbitrary-offset retrieval.
7. Apply the proposed fix and re-run steps 3-6: the valid-token requests now return `404 File not found`, while a file inside the configured media root still returns `200`.

````python
#!/usr/bin/env python3
# poc_local.py <port> <streamToken>   — replays the extracted /stream route
import sys, urllib.parse, urllib.request, urllib.error

port, token = int(sys.argv[1]), sys.argv[2]
base = f"http://127.0.0.1:{port}/stream"

def get(**q):
    url = base + "?" + urllib.parse.urlencode(q)
    try:
        with urllib.request.urlopen(url) as r:
            return r.status, r.read()
    except urllib.error.HTTPError as e:
        return e.code, e.read()

print("1. absolute / traversal paths with a valid token:")
for target in ["/etc/passwd", "/etc/hostname", "/workspace/electron/main.js",
               "/workspace/.poc-media/files/../../../../etc/hostname"]:
    st, body = get(path=target, token=token)
    print(f"   {st} {target} -> {body.splitlines()[0][:60]!r}")

print("2. without a token / with a guessed token:")
for bad in [{}, {"token": "0" * 32}]:
    st, _ = get(path="/etc/passwd", **bad)
    print(f"   {st} token={bad.get('token', '<none>')}")

print("3. arbitrary byte offset via Range:")
req = urllib.request.Request(
    base + "?" + urllib.parse.urlencode({"path": "/etc/passwd", "token": token}),
    headers={"Range": "bytes=700-800"})
try:
    with urllib.request.urlopen(req) as r:
        print("   ", r.status, r.read()[:120])
except urllib.error.HTTPError as e:
    print("   ", e.code, e.read()[:60])
```
````

## Remediation

Confine every local path served by the media route to an explicit media-root allowlist before any filesystem call. Resolve the request value to a canonical real path, resolve each configured root the same way, and accept the request only when the canonical path is a strict descendant of one of those roots; reject on any resolution failure. Apply the containment result to every downstream use — existence check, stat, codec probe, ffmpeg input and the read stream — rather than checking and then reusing the raw parameter. Treat symlinks as escapes by canonicalising with a real-path resolution rather than lexical normalisation alone, and return the same not-found response for both "missing" and "outside root" so the endpoint cannot be used to probe for file existence. Keep the token as defence in depth, but do not rely on it for this boundary: stop writing request paths and full ffmpeg command lines to the console, and stop printing the token-bearing URL at startup.

## Fix Verification

Line numbers were re-verified byte-for-byte against the CRLF-encoded source: the ffmpeg input is at line 767 and the ranged read stream at 848 (the full-file stream is 879). The patch was applied to the extracted route (`/workspace/.poc-media/fixcheck/server_fixed.js`, media root `/workspace/.poc-media/media-library`), and the PoC was re-run against it.

Gate 1 — security closure (executed): `poc_local.py` against the patched server returns `404 File not found` for `/etc/passwd`, `/etc/hostname`, `/workspace/electron/main.js`, the traversal path, and the `Range:` request, while `/workspace/.poc-media/media-library/ok.wav` returns `200` with the full 88278 bytes. Re-traced the patched path: `req.query.path` → `resolveConfinedMediaPath` (`realpathSync` plus `path.relative` containment) → `localPath` → `statSync`, `probeStreamCodecsCached`, `ffmpeg()`, `createReadStream`. All five sinks now receive `localPath` or a value derived from it, and `localPath` is `''` unless containment succeeded, so no sink remains reachable on the raw parameter.

Gate 2 — bypass review (executed): the decision is made on the `realpathSync` output, so `..` sequences are resolved before comparison rather than matched textually. A symlink placed inside the root pointing at `/etc/passwd` (`media-library/link.mp4`) returned `404`, confirming symlink escape is closed. Empty, non-string and unresolvable inputs fall out of `resolveLocalMediaPath`'s guard and are rejected. The remote arm still short-circuits on `isRemote` before the filesystem check, so the IPTV path is unaffected, and the ffmpeg line keeps `localPath || videoPath` so the remote URL still reaches ffmpeg unchanged.

Gate 3 — preserved behavior (executed): in-root media streams normally (`200`, 88278 bytes), the `403` for a missing or wrong token is unchanged, and the diff does not touch range parsing, MIME mapping, or the `cleanup`/`killStreamPipe` lifecycle.

Gate 4 — repository checks (gap stated): this checkout has no test suite, linter config, or build step, so the verification executed is the extracted route under Node v24.21.0 with real ffmpeg 9.0.2, exercising the complete request path including `ffmpeg()` and `createReadStream`. Not executed: the patch inside a real Electron process, and the Windows branch of `resolveLocalMediaPath` (literal backslash conversion), which the Linux run exercises as a different string shape — both are explicit gaps.

## Assumptions

Assumes the attacker is a local principal that can read the application's console output (main-process stdout/stderr captured to a file, a terminal scrollback, a service/wrapper log, or Chromium `--enable-logging` output) but does not already have the user's file-read privileges. Cross-origin and remote-origin reach was tested and is blocked by Chromium, so no browser-based attacker is claimed.
